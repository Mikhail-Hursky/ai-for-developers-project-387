# Как мы ведём разработку

Договорённости репозитория: формат коммитов, проверки перед коммитом и то, как
из коммитов получаются релизы. Правила одинаковы для человека и для агента.

## Формат коммитов

Используем [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ru/v1.0.0/).
Заголовок:

```
<тип>(<область>): <что делает коммит>
```

- **тип** — из списка ниже, в нижнем регистре;
- **область** — необязательная, в нижнем регистре: имя пакета или подсистемы
  (`backend`, `admin`, `slots`, `e2e`, `openapi`, `storage`, `readme`);
- **описание** — на английском, в повелительном наклонении и настоящем времени
  («add», а не «added»), с маленькой буквы, без точки в конце;
- заголовок — не длиннее 100 символов.

Тело коммита отделяется пустой строкой, строки — не длиннее 100 символов.
Пишем в нём, *что* изменилось и *почему*, обычно маркированным списком.

```
fix(storage): snapshot bookings before iterating busy_intervals

- параллельный запрос мог добавить бронь прямо во время обхода, и слот
  выдавался дважды
- срез делается один раз на запрос, поэтому сетка слотов остаётся
  согласованной
```

Ломающее изменение помечается `!` после области и футером `BREAKING CHANGE:`
с объяснением, что придётся поправить потребителям:

```
feat(openapi)!: rename slot fields to camelCase

BREAKING CHANGE: клиенты, читавшие start_at и end_at, должны перейти
на startAt и endAt.
```

### Типы и их влияние на версию

Версию считает release-please. Пока проект младше `1.0.0`, ломающее изменение
поднимает минорную версию, а не мажорную.

| Тип | Когда | Версия (до 1.0.0) | В CHANGELOG |
| --- | --- | --- | --- |
| `feat` | новая функциональность | минорная | да |
| `fix` | исправление поведения | патч | да |
| `perf` | ускорение без смены поведения | патч | да |
| `revert` | откат коммита | патч | да |
| `refactor` | внутренняя переделка | патч | да |
| `test` | тесты | патч | да |
| `docs` | документация, спеки, планы | патч | да |
| `style` | форматирование | патч | нет |
| `build` | сборка и зависимости | патч | нет |
| `ci` | конфигурация CI | патч | нет |
| `chore` | всё остальное | патч | нет |

Один коммит — одно изменение. Если в заголовке хочется написать «и», это два
коммита.

Формат проверяет job `commitlint` в [CI](.github/workflows/ci.yml): он читает
[.commitlintrc.yml](.commitlintrc.yml) и падает на коммитах, которые не
разбираются по этим правилам. Merge-коммиты и коммиты релиза
(`chore(main): release X.Y.Z`) проверку проходят.

## Коммиты, которые делает агент

Те же правила плюс несколько уточнений:

- агент коммитит только тогда, когда его об этом попросили, и не пушит без
  отдельной просьбы;
- перед коммитом агент прогоняет проверки затронутых пакетов (см. ниже) и
  сообщает результат — «зелено» без вывода команд не принимается;
- в теле коммита — что изменилось и почему, без пересказа диффа;
- в футере остаётся трейлер соавторства:

  ```
  Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
  ```

Эти же правила продублированы в [CLAUDE.md](CLAUDE.md) — файле, который агент
читает автоматически в начале сессии.

## Проверки перед коммитом

Прогоняем то, что задето изменением; CI прогонит всё целиком.

```bash
# spec/    — контракт и мок
npm run mock:check

# frontend/
npm run lint && npm test && npm run build

# backend/
uv run ruff check . && uv run ruff format --check . && uv run pytest

# e2e/     — поднимает бэкенд и прод-сборку фронтенда сам
npm test
```

Скомпилированный `spec/openapi/openapi.yaml` лежит в репозитории: после правки
`main.tsp` его нужно пересобрать (`npm run build` в `spec/`) и закоммитить.
CI сверяет их job'ом `spec`.

### Версия npm и package-lock.json

CI ставит Node 24 последней версии, то есть npm 11.17 и новее. Старый npm
записывает в `package-lock.json` не все зависимости опциональных
платформенных пакетов (например, wasm-биндинга rolldown), сам такой файл
проглатывает, а новый — падает с `npm ci can only install packages when your
package.json and package-lock.json are in sync`.

Поэтому держите локальный Node на актуальной 24-й версии, а если трогали
зависимости — проверьте установку тем же npm, что и в CI:

```bash
npx npm@latest ci
```

### Когда локально зелено, а в CI красно

Node и TypeScript ищут пакеты и типы вверх по дереву каталогов, поэтому
случайный `node_modules` в домашней папке чинит сборку на вашей машине и не
чинит её на раннере. Если расхождение непонятно, скопируйте пакет во
временный каталог **вне** домашнего (`/tmp/...`), сделайте там `npm ci` и
повторите команду: ошибка CI обычно воспроизводится сразу.

## CI

[.github/workflows/ci.yml](.github/workflows/ci.yml) запускается на пуш в `main`
и на каждый pull request. Job'ы: `commitlint`, `spec`, `frontend`, `backend` и
`e2e` (последний ждёт зелёных `frontend` и `backend`, потому что занимает
раннер дольше всех). Артефакты упавшего прогона Playwright — трейсы и
скриншоты — лежат в `playwright-test-results`.

Отдельно живёт `hexlet-check.yml`: он сгенерирован Hexlet, его не трогаем.

## Claude в обсуждениях

[.github/workflows/claude.yml](.github/workflows/claude.yml) отвечает на
`@claude` в комментарии к issue, в обсуждении pull request и в комментарии к
строке диффа. Claude читает код ветки, дифф и логи упавшего CI, а отвечает
комментарием в том же треде: прав на запись в репозиторий у прогона нет, коммиты
и ветки он не делает.

Правила из [CLAUDE.md](CLAUDE.md) действуют и здесь — отдельного промпта в
workflow нет.

Позвать Claude может только владелец репозитория: токен в секрете
`CLAUDE_CODE_OAUTH_TOKEN` личный, и чужой `@claude` расходовал бы его квоту.
Комментарий от любого другого аккаунта прогон не запускает. Чтобы дать доступ
соавтору, его логин нужно дописать в условие `if:` этого workflow.

Что нужно один раз: приложение [Claude](https://github.com/apps/claude) должно
быть установлено на репозиторий, иначе прогон падает на авторизации.

## Релизы

[release-please](https://github.com/googleapis/release-please) держит открытым
один pull request «chore(main): release X.Y.Z» и дописывает в него версию и
CHANGELOG по мере появления коммитов в `main`. Мерж этого PR ставит тег
`vX.Y.Z` и публикует GitHub Release.

Версия у проекта одна на все пакеты: release-please обновляет `version.txt`,
`CHANGELOG.md`, `.release-please-manifest.json`, поле `version` в трёх
`package.json` (и в их `package-lock.json`) и в `backend/pyproject.toml`.
Настройки — в [release-please-config.json](release-please-config.json).

Что нужно один раз включить в настройках репозитория (Settings → Actions →
General → Workflow permissions):

- **Read and write permissions** для `GITHUB_TOKEN`;
- галку **Allow GitHub Actions to create and approve pull requests**.

Известное ограничение: PR, созданный `GITHUB_TOKEN`, не запускает другие
workflow — на релизном PR не будет прогона `ci`. Изменения в нём
сгенерированы автоматически и уже проверены на `main`; если прогон всё-таки
нужен, заведите Personal Access Token и передайте его в `token:`
[workflow'а релиза](.github/workflows/release-please.yml).

Выпустить версию вручную (например, зафиксировать `1.0.0`) можно коммитом с
футером `Release-As: 1.0.0`.
