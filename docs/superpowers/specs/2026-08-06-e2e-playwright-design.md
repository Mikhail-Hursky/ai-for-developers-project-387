# E2E-тесты на Playwright — дизайн

Дата: 2026-08-06

## Задача

Покрыть сквозным браузерным тестом полный путь продукта: владелец создаёт тип
встречи в админке → гость видит его в списке → выбирает день и слот → заполняет
форму → получает подтверждение → бронь появляется в «Предстоящих встречах»
админки. Плюс три негативных сценария, где фронтенд и бэкенд обязаны сойтись:
занятый слот, дубликат идентификатора типа встречи, неизвестный тип встречи.

Юнит-тесты уже есть по обе стороны: vitest во [frontend/](../../../frontend) со
`stubFetch` и pytest в [backend/](../../../backend) через `TestClient`. Ни те,
ни другие не проверяют, что фронт и бэк договариваются друг с другом по-настоящему
— это и есть предмет E2E.

Прод-код в этой задаче не меняется.

## Решения

| Вопрос | Решение |
|---|---|
| Против чего гоняем | Настоящий бэкенд FastAPI, не Prism-мок |
| Кто поднимает серверы | Два `webServer` в `playwright.config.ts` |
| Фронтенд | Прод-сборка через `vite preview` на 4173 |
| Размещение | Новый пакет `e2e/` рядом с `spec/`, `frontend/`, `backend/` |
| Параллельность | `workers: 1`, `fullyParallel: false` |
| Изоляция | Уникальный `id` типа встречи на тест + выбор первого свободного слота |
| Часовой пояс | `timezoneId: 'UTC'` в конфиге |
| Браузер | Только chromium |
| Локаторы | Роли, лейблы и текст; ни одного `data-testid` |
| CI | Не трогаем: единственный workflow сгенерирован Hexlet и правке не подлежит |

Не делаем: кроссбраузерность, мобильные viewport'ы, визуальные снапшоты,
проверки клиентской валидации форм (покрыты vitest), сценарий недоступного
бэкенда, тестовую ручку сброса состояния.

## Почему настоящий бэкенд, а не Prism

Prism stateless: созданный тип встречи не появится в `GET /event-types`, а бронь
— в `GET /admin/bookings/upcoming`. Именно поэтому
[`EventTypesAdmin`](../../../frontend/src/features/admin/EventTypesAdmin.tsx)
дописывает созданный тип в список локально. Сквозной флоу «создал → увидел →
записался» на моке проверить нечем: он вырождается в проверку локального
состояния React. Настоящий бэкенд держит состояние в памяти процесса, чего для
E2E достаточно.

## Запуск окружения

`playwright.config.ts` поднимает оба сервера сам, так что `npx playwright test`
самодостаточен.

| webServer | Команда | cwd | Порт |
|---|---|---|---|
| Бэкенд | `uv run uvicorn app.main:app --port 3000` | `../backend` | 3000 |
| Фронтенд | `npm run build && npm run preview -- --port 4173 --strictPort` | `../frontend` | 4173 |

Фронтенд собирается с `VITE_API_BASE_URL=http://localhost:3000/api` в `env`
процесса — переменная читается на этапе сборки, поэтому задавать её нужно
именно команде `build`, а не `preview`. Файл `frontend/.env` при этом не
трогается: у разработчика там может быть адрес мока.

Порт 4173 уже перечислен в `CORS_ORIGINS`
[бэкенда](../../../backend/app/config.py) — правок серверного кода не требуется.

`baseURL: 'http://localhost:4173'`, `reuseExistingServer: !process.env.CI`.

`timezoneId: 'UTC'`: бэкенд считает сетку слотов в UTC, фронтенд форматирует
время в поясе браузера. Без пина метки слотов, заголовки дней и группировка
броней по дням в админке зависели бы от машины, а в поясах восточнее UTC+6
сегодняшние слоты уезжали бы на следующий календарный день.

## Изоляция при общем хранилище

Хранилище бэкенда — одно на весь прогон, и правило занятости не различает типы
встреч: бронь на 10:00 закрывает 10:00 для любого другого типа. Отсюда два
следствия для устройства тестов.

1. `workers: 1`, `fullyParallel: false`. Параллельные тесты отбирали бы слоты
   друг у друга.
2. Тест никогда не жёстко задаёт время. Он берёт **первый свободный слот** из
   сетки: UI по умолчанию открывает первый день с непустым списком, тест жмёт
   первую кнопку в группе «Свободные слоты». Брони, оставшиеся от предыдущих
   тестов, просто сдвигают выбор.

Тип встречи в каждом тесте свой: `id` вида `e2e-<slug>-<Date.now()>`,
длительность 30 минут. Ничего не чистим после тестов — бэкенд стартует пустым
на каждый прогон.

## Сценарии

### 1. Сквозной путь от создания типа до брони в админке

`e2e/tests/full-flow.spec.ts`

1. `/admin?tab=event-types` → «Создать тип» → форма → «Создать».
2. Алерт «Тип встречи «…» создан», карточка типа в списке админки.
3. `/booking` → карточка нового типа → страница `/booking/<id>`.
4. Выбор первого свободного слота → форма гостя → «Записаться».
5. Экран «Вы записаны»: имя гостя, email, название типа встречи.
6. `/admin` (вкладка «Предстоящие встречи») → карточка брони с именем гостя,
   email и названием типа встречи.

### 2. Слот заняли, пока гость заполнял форму (409)

`e2e/tests/slot-conflict.spec.ts`

Гость доходит до формы и выбирает слот. Тест через `request`-фикстуру шлёт
`POST /api/bookings` на тот же `startAt` от имени другого гостя. Гость жмёт
«Записаться» → жёлтый баннер «Это время уже заняли, выберите другое», форма
гостя скрыта, сетка слотов перезапрошена и занятого времени в ней больше нет.

Конфликтующая бронь создаётся HTTP-запросом, а не во второй вкладке браузера:
это точная модель гонки и не зависит от таймингов рендера второй страницы.

### 3. Дубликат идентификатора типа встречи (409)

`e2e/tests/event-type-duplicate.spec.ts`

Создать тип, снова открыть модалку с тем же `id` → ошибка под полем
«Идентификатор», модалка остаётся открытой.

### 4. Неизвестный тип встречи (404)

`e2e/tests/event-type-missing.spec.ts`

Переход на `/booking/e2e-missing-<Date.now()>` → «Тип встречи не найден» и
кнопка «Выбрать тип встречи», ведущая на `/booking`.

## Локаторы

Только роли, лейблы и текст: `getByRole`, `getByLabel`, `getByText`. Прод-код не
трогаем и `data-testid` не добавляем — вся нужная семантика уже есть:

- у сетки слотов `role="group" aria-label="Свободные слоты"`, у списка дней
  `role="group" aria-label="Дни окна записи"`;
- поля Mantine связаны с лейблами («Идентификатор», «Название», «Описание»,
  «Длительность, минут», «Имя», «Email», «Комментарий»);
- кнопки и заголовки уникальны по тексту в пределах своего экрана.

## Структура

```
e2e/
  package.json           @playwright/test; скрипты test, test:ui, report
  playwright.config.ts   два webServer, baseURL, timezoneId, workers: 1
  .gitignore             test-results/, playwright-report/, node_modules/
  README.md              как запускать, что требуется локально
  fixtures/
    eventType.ts         createEventType(page, values) — проход по модалке админки
    booking.ts           pickFirstSlot(page), fillGuestForm(page, values)
    ids.ts               uniqueEventTypeId(slug)
  tests/
    full-flow.spec.ts
    slot-conflict.spec.ts
    event-type-duplicate.spec.ts
    event-type-missing.spec.ts
```

### Хелперы

| Функция | Что делает |
|---|---|
| `uniqueEventTypeId(slug)` | Возвращает `e2e-<slug>-<Date.now()>` |
| `createEventType(page, values)` | Открывает модалку в админке, заполняет и отправляет форму, дожидается алерта об успехе |
| `pickFirstSlot(page)` | Жмёт первую кнопку в группе «Свободные слоты» и возвращает `startAt` выбранного слота |
| `fillGuestForm(page, values)` | Заполняет имя, email, комментарий и жмёт «Записаться» |

`pickFirstSlot` достаёт `startAt` из ответа `GET /api/event-types/<id>/slots`,
перехваченного через `page.waitForResponse`: в разметке кнопки лежит только
отформатированное локальное время, а сценарию 2 нужен точный ISO-момент для
конфликтующей брони.

## Скрипты

Из каталога `e2e/`:

```bash
npm install
npx playwright install chromium
npm test          # playwright test
npm run test:ui   # playwright test --ui
npm run report    # playwright show-report
```

Требования к машине: установленный `uv` (для бэкенда) и зависимости фронтенда
(`npm ci` в `frontend/`).

## CI

Единственный workflow в репозитории —
[`.github/workflows/hexlet-check.yml`](../../../.github/workflows/hexlet-check.yml)
с пометкой «DO NOT DELETE OR EDIT THIS FILE». Он не трогается, отдельный
workflow для E2E в эту задачу не входит. Конфиг при этом готов к CI:
`reuseExistingServer: !process.env.CI` и `retries: process.env.CI ? 1 : 0`.

## Известное ограничение

Тесты зависят от реальных часов. Рабочее окно бэкенда — будни 10:00–18:00 UTC,
и прогон вечером в пятницу означает, что первый день со слотами — понедельник.
Логику это не ломает: нигде не проверяется конкретная дата или время, только
«первый доступный». Сделать время детерминированным можно было бы подменой
`app.clock.utc_now` через переменную окружения, но это изменение прод-кода ради
тестов, и в эту задачу оно не входит.
