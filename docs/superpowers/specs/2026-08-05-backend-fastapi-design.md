# Бэкенд на FastAPI — дизайн

Дата: 2026-08-05

## Задача

Реализовать бэкенд календаря бронирования по контракту [spec/main.tsp](../../../spec/main.tsp):
шесть ручек, правило занятости и окно записи на 14 дней. Основные бизнес-правила
живут на бэкенде — до этого шага их имитировал Prism-мок
(см. [дизайн мока](2026-08-02-prism-mock-design.md)).

База данных не нужна: хранилище в памяти, данные сбрасываются при рестарте.

Фронтенд в эту задачу не входит. Он продолжает смотреть на мок; переключение
`VITE_API_BASE_URL` — отдельный шаг, README бэкенда описывает, что для этого
поменять.

## Решения

| Вопрос | Решение |
|---|---|
| Стек | Python 3.13, `uv`, FastAPI, pydantic v2, uvicorn |
| Структура | Слои: HTTP-роутеры → бизнес-правила → хранилище |
| Расписание | Константы в `config.py`: будни, 10:00–18:00 UTC, шаг = длительность типа |
| Начальные данные | Хранилище стартует пустым: ни типов событий, ни броней |
| Адрес | `http://localhost:3000/api` — как в `@server` контракта |
| Формат времени | `2026-08-05T10:00:00Z`: суффикс `Z`, точность до секунд |
| Имена полей | В Python `snake_case`, на проводе `camelCase` через alias-генератор |
| Тесты | pytest: чистые функции сетки отдельно, ручки через `TestClient` |

Не делаем: редактирование и удаление типов событий, аутентификацию, пагинацию,
healthcheck, persistence. Контракт их не описывает, требование не содержит.

## Почему слои, а не один модуль

Самое сложное в задаче — правила бронирования и генерация сетки слотов, и править
их придётся чаще всего. Роутеры только разбирают запрос и отдают ответ; сетка слотов
и проверки брони — модули, которые ничего не знают про FastAPI, поэтому тестируются
без HTTP. Гексагональная архитектура с портами и абстрактным репозиторием оправдана
перед приходом реальной БД; на in-memory-хранилище это слои без выгоды.

## Структура

```
backend/
  pyproject.toml         fastapi, uvicorn, pydantic[email]; dev: pytest, httpx, ruff
  README.md              запуск, отличия от мока, что менять в VITE_API_BASE_URL
  app/
    main.py              create_app(): CORS, роутеры под /api, обработчики ошибок
    config.py            рабочие часы, окно записи, lead time, CORS-origins
    clock.py             utc_now() как FastAPI-зависимость — в тестах подменяется
    schemas.py           pydantic-модели контракта
    errors.py            ApiError + handlers → {code, message, errors}
    storage.py           Storage: dict типов, dict броней, Lock
    slots.py             чистые функции: сетка дня, окно 14 дней, доступность
    booking.py           правила создания брони
    api/
      event_types.py     GET /event-types, /{eventTypeId}, /{eventTypeId}/slots
      bookings.py        POST /bookings
      admin.py           POST /admin/event-types, GET /admin/bookings/upcoming
  tests/
    conftest.py          приложение с замороженным временем и чистым хранилищем
    test_slots.py        сетка, окно, вычитание броней
    test_event_types.py  список, чтение по id, создание, дубликат
    test_bookings.py     создание, 404/422/409

```

Запуск: `uv run uvicorn app.main:app --port 3000 --reload`.

## Сетка слотов

Константы `config.py`:

```
WINDOW_DAYS = 14           WORKDAYS = пн..пт        LEAD_TIME_MINUTES = 5
WORK_DAY_START_HOUR = 10   WORK_DAY_END_HOUR = 18   (оба по UTC)
```

**Сетка дня.** Первый слот начинается в 10:00 UTC, шаг равен `durationMinutes`
типа события, слот попадает в сетку пока `slot_end <= 18:00`. Для 30-минутного типа
это 16 слотов (10:00 … 17:30), для 90-минутного — 5 (последний 16:00–17:30, потому
что следующий закончился бы в 19:00). Суббота и воскресенье дают пустую сетку,
но день в ответе присутствует: контракт требует все 14 дней окна.

**Окно записи.** 14 дней, первый — текущая дата по UTC. `windowStartDate` и
`windowEndDate` в ответе считаются от неё же.

**Доступность** = сетка минус два множества:

- слоты, начинающиеся раньше `now + LEAD_TIME_MINUTES`, — записаться на встречу,
  которая вот-вот начнётся, нельзя. Слот доступен при `slot_start >= now + lead`;
- слоты, пересекающиеся с любой бронью **любого** типа события.

Пересечение считается по интервалам, а не по равенству начала: `slot_start <
booking.end_at and booking.start_at < slot_end`. Это следствие правила занятости
из контракта при разных длительностях типов — бронь на 60 минут в 10:00 закрывает
15-минутный слот в 10:30.

## Правила бронирования

`POST /bookings` проверяет запрос в порядке, заданном контрактом:

| Шаг | Провал |
|---|---|
| Схема тела: формат `eventTypeId`, email, длины строк | `422 validation_failed` + `errors[]` |
| Тип события существует | `404 not_found` |
| `startAt` — начало слота сетки этого типа, внутри окна, не раньше `now + 5 мин` | `422 validation_failed`, поле `startAt` |
| Интервал брони не пересекается ни с одной существующей бронью | `409 slot_already_booked` |

Проверка «`startAt` лежит на сетке» переиспользует ту же функцию сетки, что и
`GET /slots`: иначе выдача слотов и их приём со временем разъедутся.

Шаги 3 и 4 разделены сознательно. Время вне сетки, вне окна или в прошлом —
ошибка клиента, и повторный запрос с тем же телом её не исправит (422). Занятый
слот — гонка: слот был свободен, когда гость его увидел, и фронту достаточно
перезапросить слоты (409).

Создание брони выполняется под `threading.Lock`: между проверкой занятости и
вставкой не должно вклиниться второе создание. Иначе два одновременных запроса
на один слот оба прошли бы проверку и правило занятости нарушилось бы.

`endAt` брони сервер считает сам как `startAt + durationMinutes`; в теле запроса
его нет. В ответе бронь содержит вложенный `eventType` целиком — снимок на момент
создания не нужен, типы не редактируются.

## Формат ошибок

Четыре ответа контракта, все с полями `code` и `message`:

| Код | `code` | Когда |
|---|---|---|
| 404 | `not_found` | Неизвестный `eventTypeId` |
| 409 | `slot_already_booked` | Пересечение с существующей бронью |
| 409 | `event_type_already_exists` | Тип события с таким `id` уже есть |
| 422 | `validation_failed` | Ошибки полей, детали в `errors[]` |

FastAPI по умолчанию отдаёт `422 {"detail": [...]}`, что контракту не
соответствует. `RequestValidationError` перехватывается и переводится в
`{code, message, errors: [{field, message}]}`, где `field` — camelCase-имя поля
из запроса. Собственные ошибки бросаются как исключения `ApiError` и
превращаются в ответ таким же обработчиком.

**Паттерн `eventTypeId` в пути не проверяется.** Контракт для
`GET /event-types/{eventTypeId}` разрешает только 200 и 404, поэтому любой
неизвестный или неправильно оформленный id в пути — это 404. В теле
`POST /bookings` тот же паттерн работает и даёт 422.

## Время

На проводе — `2026-08-05T10:00:00Z`: суффикс `Z`, точность до секунд, как в моке.
Достигается сериализатором поля, потому что pydantic по умолчанию пишет `+00:00`.

На входе `startAt` без таймзоны отклоняется с 422: контракт описывает поле как
`utcDateTime`, и молчаливая трактовка наивного времени как UTC прятала бы ошибку
клиента. Время с любым другим смещением приводится к UTC.

Единая точка получения «сейчас» — `clock.utc_now()`, подключённая как
FastAPI-зависимость. Тесты ручек подменяют её через `dependency_overrides` и
получают фиксированное время; чистые функции сетки принимают `now` аргументом,
поэтому в подмене не нуждаются.

## CORS

`CORSMiddleware` с origin'ами из `config.py`: `http://localhost:5173` (Vite dev)
и `http://localhost:4173` (Vite preview). Без этого браузер не пустит фронтенд
к бэкенду на другом порту.

## Тестирование

Разделение по уровням: правила — без HTTP, ручки — через HTTP.

`test_slots.py` — чистые функции: 14 дней в окне, пустые выходные, шаг сетки для
разных длительностей, последний слот не выходит за 18:00, отсечение по lead time,
вычитание брони своего типа и пересекающейся брони чужого типа.

`test_event_types.py` — пустой список на старте, создание, чтение созданного,
404 на неизвестный id, 409 на дубликат, 422 на неверный `id` и `durationMinutes`
с проверкой формы `errors[]`.

`test_bookings.py` — успешное создание (201, `endAt` посчитан, бронь исчезла из
слотов), 404 на неизвестный тип, 422 на время вне сетки / вне окна / в прошлом /
без таймзоны, 409 на повтор того же слота и на пересечение с бронью другого типа.

`test_admin.py` — предстоящие встречи отсортированы по возрастанию `startAt`,
прошедшие в список не попадают.

## Следствие пустого хранилища

Сразу после старта `GET /event-types` возвращает `[]`, и главная страница фронта
будет пустой, пока владелец не создаст тип события через админку. Это ожидаемое
поведение, а не ошибка, — README бэкенда говорит об этом явно и приводит готовый
`curl` для создания первого типа.
