# Claude ревьюит pull request — дизайн

Дата: 2026-08-17

## Задача

Сделать так, чтобы каждый открытый pull request получал ревью от Claude без
отдельной просьбы.

Два существующих воркфлоу отзываются только на обращение: `claude.yml` — на
`@claude` в комментарии, `claude-implement.yml` — на команду `@claude implement`
(см. [дизайн от 17.08](2026-08-17-claude-implement-design.md)). Попросить ревью
через `@claude` можно и сейчас, но это ручное действие, а ответ приходит одним
текстом в треде, без привязки к строкам диффа.

## Решения

| Вопрос | Решение |
|---|---|
| Событие | `pull_request`, типы `opened`, `reopened`, `ready_for_review` |
| Файл | Новый `.github/workflows/claude-review.yml` |
| Область | Только PR из этого репозитория; черновики пропускаются |
| PR от `claude[bot]` | Ревьюятся, для этого нужен `allowed_bots: claude` |
| Режим action'а | Agent mode: свой `prompt` без `track_progress` |
| Права | `contents: read`, `pull-requests: write`, `id-token: write` |
| Форма ревью | Построчные комментарии плюс сводный через `gh pr comment` |
| Concurrency | По номеру PR, без отмены начатого прогона |

Не делаем: ревью на каждый пуш в ветку PR, ревью черновиков, ревью PR из форков,
запуск тестов и линтеров внутри прогона, формальное ревью с Approve.

## Workflow

```yaml
name: claude-review

on:
  pull_request:
    types: [opened, reopened, ready_for_review]

concurrency:
  group: claude-review-${{ github.event.pull_request.number }}
  cancel-in-progress: false

jobs:
  claude-review:
    name: claude-review
    if: >-
      github.event.pull_request.head.repo.full_name == github.repository
      && !github.event.pull_request.draft
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
      id-token: write
    steps:
      - uses: actions/checkout@v7
      - uses: anthropics/claude-code-action@v1
        with:
          claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
          allowed_bots: claude
          prompt: |
            # критерии ревью, см. раздел «Промпт»
          claude_args: >-
            --allowedTools "Read,Grep,Glob,mcp__github_inline_comment__create_inline_comment,Bash(gh pr comment:*),Bash(gh pr diff:*),Bash(gh pr view:*)"
```

Комментарии в самом файле подробнее — здесь снимок структуры.

## Почему только открытие, а не каждый пуш

`synchronize` означал бы полный прогон на каждый fixup-пуш: правишь замечание —
получаешь новое ревью, где половина замечаний та же самая. Квоту это расходует
линейно по числу пушей, а пользы добавляет мало.

Ревью на открытии плюс `@claude` по просьбе покрывает те же случаи, но повторный
проход запускает человек и тогда, когда он нужен.

`ready_for_review` в списке типов не роскошь, а необходимость: у PR, открытого
черновиком, событие `opened` отсекается проверкой на `draft`, и без третьего типа
такой PR не отревьюился бы никогда.

## Почему только PR из этого репозитория

На событии `pull_request` из форка GitHub не передаёт секреты репозитория:
`CLAUDE_CODE_OAUTH_TOKEN` пришёл бы пустым, и прогон упал бы на авторизации.
Обойти это можно только через `pull_request_target`, который выполняет код
базовой ветки с секретами при доступном чужом диффе — для публичного репозитория
это плохая сделка.

Условие `head.repo.full_name == github.repository` заодно закрывает вопрос
авторизации. У двух других воркфлоу в `if:` стоит сверка с владельцем, потому что
комментарий может написать любой; здесь этого не нужно — ветку в самом
репозитории создаёт только тот, у кого есть доступ на запись.

## Почему PR от claude[bot] нужен allowed_bots

`checkHumanActor` вызывается в обоих режимах action'а (`src/modes/agent/index.ts`
и `src/modes/tag/index.ts`) и падает, если тип актора не `User`. PR, открытый
Claude по команде `@claude implement`, приходит от `claude[bot]`, то есть без
`allowed_bots` он не отревьюился бы вовсе — и это самый нужный для ревью случай.

В списке суффикс `[bot]` отрезается, поэтому значение — просто `claude`.

Проверка «свежий прогон ревьюит свой же код» здесь несостоятельна: контекста
предыдущего прогона у ревьюера нет, он видит только дифф. Это вторая пара глаз,
а не самопроверка.

## Почему agent mode

`prompt` без `track_progress` оставляет action в agent mode. Tag mode добавил бы
служебный комментарий с прогрессом — третью сущность в треде рядом с построчными
замечаниями и сводным комментарием. Ветка и коммиты, за которыми обычно идут в
tag mode, ревьюеру не нужны.

Ограничение: в agent mode дефолтного набора инструментов нет, поэтому `Read`,
`Grep` и `Glob` перечислены в `--allowedTools` явно, а не оставлены на неявные
дефолты CLI.

## Промпт

Общий «code quality» из примеров документации заменён на то, что специфично для
этого репозитория:

- контракт: `spec/main.tsp` и собранный `spec/openapi/openapi.yaml` должны
  совпадать, а `backend/` и `frontend/` — соответствовать контракту;
- ошибки и краевые случаи в логике;
- тесты: покрыто ли изменение и не подогнан ли тест под реализацию;
- расхождения с правилами из `CLAUDE.md` и `CONTRIBUTING.md`.

Запреты в промпте не менее важны, чем критерии: не пересказывать дифф, не хвалить
код, не лезть в стиль, который уже проверяют ruff и ESLint, не пытаться запускать
тесты и не дублировать ревью текстом ответа. Без них ревью превращается в длинный
комментарий, который никто не читает.

Форма: построчные замечания через
`mcp__github_inline_comment__create_inline_comment` с `confirmed: true`, сводка
через `gh pr comment`, «замечаний нет» — одной строкой.

## Проверка

1. `actionlint .github/workflows/` — если линтер есть в системе.
2. Живой прогон: открыть PR с заведомо спорным кодом и убедиться, что пришли
   построчные замечания и сводный комментарий, а не один длинный текст.
3. Черновик: открыть PR как draft — прогон должен получить статус `skipped`;
   нажать «Ready for review» — ревью должно прийти.
4. PR от `claude[bot]`: позвать `@claude implement` в issue и проверить, что
   созданный PR отревьюен. Это же подтверждает, что `allowed_bots` работает.
5. Проверить, что ревью не мешает `ci.yml`: два воркфлоу на одном событии
   `pull_request` независимы и в разных группах concurrency.

## Известные ограничения

- **Формального ревью не будет.** Approve и Request changes для Claude закрыты на
  уровне action'а, галочка в PR не появится — только комментарии.
- **Одно ревью на PR.** Повторное — по просьбе через `@claude`.
- **PR из форков не ревьюятся.** Причина в секретах, см. выше.
- **Ревьюится результат слияния с базой.** `actions/checkout` на событии
  `pull_request` выкладывает merge-коммит, а не голову ветки; для ревью это
  скорее плюс, но замечание может указывать на строку, которой в ветке нет.
- **Тесты не запускаются.** Инструментов для этого у ревьюера нет намеренно;
  зелёный или красный CI виден в самом PR.
