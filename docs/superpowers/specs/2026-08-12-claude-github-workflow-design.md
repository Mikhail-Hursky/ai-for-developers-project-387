# Вызов Claude из issue и PR — дизайн

Дата: 2026-08-12

## Задача

Сделать так, чтобы владелец репозитория мог позвать Claude в обсуждении:
написал `@claude ...` в комментарии к issue или к PR — получил ответ в том же
треде.

Сейчас в `.github/workflows/` три файла: `ci.yml` (проверки пакетов),
`release-please.yml` (версии и релизы) и `hexlet-check.yml` (автотесты курса,
трогать нельзя). Ни один из них с Claude не связан. Секрет
`CLAUDE_CODE_OAUTH_TOKEN` в репозитории уже заведён.

На этом этапе Claude только отвечает текстом: ни коммитов, ни веток, ни PR.

## Решения

| Вопрос | Решение |
|---|---|
| Файл | Новый `.github/workflows/claude.yml`, `ci.yml` не меняется |
| События | `issue_comment`, `pull_request_review_comment`, `pull_request_review` |
| Кто может звать | Только владелец репозитория |
| Триггер-фраза | `@claude`, дефолт action'а |
| Режим action'а | Tag mode: `prompt` не задаём |
| Права | `contents: read`, `issues: write`, `pull-requests: write`, `id-token: write`, `actions: read` |
| Действия Claude | Чтение кода, диффа и логов CI, ответ комментарием |
| Concurrency | По номеру issue или PR, без отмены начатого прогона |
| Версия action'а | `anthropics/claude-code-action@v1` |

Не делаем: срабатывание по открытию issue, по assign и label, автоматические
ветки и PR, запуск проверок проекта внутри прогона, свой `prompt`.

## Workflow

```yaml
name: claude

# Claude отвечает в обсуждении, когда его позвали: @claude в комментарии.
# Три события покрывают три места, где можно написать комментарий: тред issue
# и обсуждение PR (оба — issue_comment), комментарий к строке диффа и тело
# ревью.
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
  pull_request_review:
    types: [submitted]

# Пока один комментарий обрабатывается, следующий по тому же обсуждению ждёт
# очереди — иначе два ответа перемешаются в одном треде. Отменять начатый
# прогон нельзя: он уже пишет комментарий. Номера issue и PR в репозитории
# из одной последовательности, так что группы не пересекаются.
concurrency:
  group: claude-${{ github.event.issue.number || github.event.pull_request.number }}
  cancel-in-progress: false

jobs:
  claude:
    name: claude
    # Автор должен быть владельцем репозитория: чужой @claude не поднимает job
    # вообще. Логин и текст лежат в разных полях — в comment у комментариев,
    # в review у тела ревью, поэтому оба берутся через ||. Проверка на
    # триггер-фразу здесь — чтобы не тратить раннер на каждый комментарий;
    # сам action её всё равно перепроверит.
    if: >-
      (github.event.comment.user.login || github.event.review.user.login)
        == github.repository_owner
      && contains(github.event.comment.body || github.event.review.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      # Только чтение: правок и веток на этом этапе не делаем.
      contents: read
      # Ответ в треде issue или в обсуждении PR и служебный комментарий
      # с прогрессом.
      issues: write
      # Ответы на комментарии к строкам диффа.
      pull-requests: write
      # OIDC-токен: по нему action ходит в GitHub от имени claude[bot].
      id-token: write
      # Чтение прогонов и логов CI — см. additional_permissions ниже.
      actions: read
    steps:
      # Без клона Claude не увидит ни код, ни CLAUDE.md с правилами репозитория.
      # Ветку PR action доберёт сам, см. раздел про checkout.
      - uses: actions/checkout@v7
      - uses: anthropics/claude-code-action@v1
        with:
          claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
          # Без этого Claude не видит результаты прогонов, даже когда права
          # actions: read выданы job'у.
          additional_permissions: |
            actions: read
```

## Почему tag mode, а не свой prompt

У action'а два режима. С заданным `prompt` он выполняет нашу инструкцию и не
занимается тредом — это для автоматизации вроде «отревьюй каждый PR». Без
`prompt` включается tag mode: action сам собирает контекст обсуждения
(заголовок, тело, комментарии, дифф в PR), ставит служебный комментарий с
прогрессом и отвечает на реплику, в которой его позвали. Для диалога нужен
именно он.

Инструкции Claude берёт из `CLAUDE.md` — тот же файл, что и в локальной сессии,
поэтому договорённости репозитория действуют и в Actions без дублирования в
workflow.

## События: почему именно эти три

Комментарий в обсуждении PR в API — это `issue_comment`, а не событие PR:
одно событие покрывает и тред issue, и «разговорную» часть PR. Отдельные
события нужны только для ревью: `pull_request_review_comment` — комментарий,
привязанный к строке диффа, `pull_request_review` — сопроводительный текст
самого ревью (тот, что пишут рядом с Approve или Request changes).

Событий `issues` и `pull_request` в списке нет: Claude отзывается на обращение,
а не на само появление issue или PR.

## Почему только владелец

Репозиторий публичный, а токен в `CLAUDE_CODE_OAUTH_TOKEN` — личный: любой
`@claude` от постороннего расходовал бы чужую квоту.

Проверка стоит в `if:` job'а, то есть до запуска раннера: чужой комментарий не
поднимает job, ничего не пишется в тред, токены не тратятся. Логин не
хардкодится — условие не сломается при переименовании или переносе репозитория.

Поля с автором и текстом у событий разные, поэтому в условии два `||`:

| Событие | Автор | Текст |
|---|---|---|
| `issue_comment` | `comment.user.login` | `comment.body` |
| `pull_request_review_comment` | `comment.user.login` | `comment.body` |
| `pull_request_review` | `review.user.login` | `review.body` |

У неподходящего события своё поле пустое, и `||` берёт второе. Ревью без текста
даёт пустую строку — `contains` на ней возвращает `false`, job не стартует.
Скобки вокруг `||` обязательны: в выражениях GitHub `==` связывает сильнее, и
без них условие развалилось бы на `login || (login == owner)`.

Встроенная проверка action'а (нужен write-доступ) остаётся вторым слоем, но она
слабее: write-доступ можно выдать нескольким людям, а владелец один. Ботов
условие отсекает заодно — их логин с владельцем не совпадёт, плюс у
`allowed_bots` дефолт пустой.

Побочный эффект осознанный: соавтору `@claude` работать не будет, пока его
логин не добавят в условие.

## Почему read-only держится на правах, а не на просьбе

Запись в репозиторий из этого прогона невозможна технически, а не по инструкции:
`contents` выдан только на чтение. Даже если Claude решит поправить файл,
отправить изменение будет некуда. Bash в action'е по умолчанию выключен, поэтому
команды проекта в прогоне тоже не запускаются.

`pull-requests: write` и `issues: write` — это право писать комментарии, а не
код: содержимое PR ими не меняется, состояние PR (merge, close, метки) Claude в
tag mode не трогает. `id-token: write` вообще не про репозиторий: это OIDC-токен
для обмена на токен GitHub-приложения, без него action не сможет комментировать
от имени `claude[bot]`.

## Зачем actions: read

Самый частый вопрос в PR — «почему упал CI». Без доступа к прогонам Claude может
только гадать по диффу; с ним он читает статус job'ов и логи упавшего шага и
отвечает по факту. Право чисто на чтение, ничего запускать или отменять оно не
позволяет.

Тонкость: одного `actions: read` в блоке `permissions` мало — инструменты для
работы с прогонами включаются, только если то же самое передано в
`additional_permissions`. Забыть вторую половину легко, и симптом будет глухой:
Claude просто скажет, что логов не видит.

## Checkout: ветку PR action доберёт сам

Для события `issue_comment` `actions/checkout` клонирует ветку по умолчанию, а
не ветку PR — GitHub не подставляет head PR в этот контекст. Само по себе это
означало бы, что в PR Claude рассуждает по `main`.

Действия по ветке action берёт на себя: `src/github/operations/branch.ts` для
открытого PR делает `git fetch origin pull/<номер>/head:<ветка>` и
`git checkout` этой ветки — включая PR из форков, где ветки в нашем remote нет
вообще. Для issue и для закрытого PR он создаёт локальную ветку от исходной
(`git checkout -b`); при `contents: read` она остаётся локальной, отправить её
некуда.

Поэтому в workflow достаточно обычного `actions/checkout@v7` без `ref` и без
`fetch-depth` — глубина по умолчанию равна 1, а нужные коммиты action дотянет
сам.

## Предусловие вне репозитория

Приложение [`github.com/apps/claude`](https://github.com/apps/claude) должно
быть установлено на репозиторий — на нём держится авторизация из `id-token`.
Проверить установку из CLI нельзя: у токена `gh` не хватает прав на
`/repos/{repo}/installation`. Если приложения нет, прогон падает на шаге
авторизации с явной ошибкой.

## Проверка

1. `actionlint .github/workflows/claude.yml` — если линтер есть в системе;
   иначе синтаксис проверяет сам GitHub при первом прогоне.
2. Живой прогон в issue: создать issue, написать в комментарии `@claude` с
   вопросом по репозиторию, дождаться `gh run watch` и ответа в треде. Ответ
   должен опираться на код — это подтверждает, что `checkout` отработал.
3. Живой прогон в PR: в комментарии к строке диффа спросить `@claude` про
   изменённый код. Ответ должен ссылаться на состояние ветки PR, а не `main` —
   это подтверждает, что action переключил ветку.

Проверить негативный сценарий (комментарий от постороннего аккаунта не
запускает job) на своём репозитории нечем. Условие в `if:` разбирается
статически и не зависит от рантайма, поэтому здесь достаточно чтения кода.

## Известные ограничения

- **Только обращение по `@claude`.** Ни открытие issue, ни открытие PR ничего не
  запускают: чтобы Claude отреагировал, его нужно позвать.
- **Один участник.** Условие привязано к владельцу репозитория.
- **PR из форков.** Позвав `@claude` в таком PR, владелец пускает Claude читать
  код из чужой ветки, и инструкции могут оказаться в самом диффе. При
  `contents: read` и выключенном Bash худший исход — неудачный ответ в треде,
  но помнить об этом стоит.
- **Ответ не мгновенный.** Прогон поднимает раннер, клонирует репозиторий и
  ставит Claude Code — первые секунды в треде виден только комментарий с
  прогрессом.
- **Свежесть кода.** Claude видит состояние ветки на момент прогона, а не
  рабочую копию на машине.
