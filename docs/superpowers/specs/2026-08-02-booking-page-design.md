# Фронтенд: страница записи — дизайн

Дата: 2026-08-02

## Задача

Реализовать поток записи гостя: выбор типа встречи, выбор дня и свободного
слота, форма контактов, подтверждение. Заглушка `/booking` из предыдущей
итерации заменяется двумя рабочими страницами.

Бэкенд по-прежнему не пишем: работаем против Prism-мока из `spec/`
(см. [дизайн мока](2026-08-02-prism-mock-design.md) и
[дизайн главной](2026-08-02-frontend-home-design.md)).

## Решения

| Вопрос | Решение |
|---|---|
| Поток | Две колонки (дни + слоты), форма раскрывается ниже после выбора слота |
| `/booking` без id | Отдельная страница выбора типа встречи |
| Выбор дня | Свой список 14 дней из ответа API; `@mantine/dates` не подключаем |
| Часовой пояс | Локальное время браузера с подписью зоны; в API уходит UTC-строка из ответа |
| Форма | `@mantine/form` |
| Экран успеха | Данные из ответа `POST /bookings`, как есть |
| Совместимость с моком | Заголовок `Prefer: example=<eventTypeId>` на запросы по id |

## Ограничения мока

Два ограничения Prism определяют часть решений.

**Примеры выбираются заголовком.** У `GET /event-types/{id}` и
`GET /event-types/{id}/slots` примеры названы по идентификатору типа события.
Без заголовка `Prefer: example=<id>` Prism отдаёт первый пример — слоты
`intro-call` (30 минут) для любого типа. Поэтому клиент шлёт этот заголовок
на оба запроса. Настоящий бэкенд его проигнорирует, удалять код не придётся.

**Ответ на создание брони фиксирован.** `POST /bookings` всегда возвращает одну
и ту же бронь из фикстуры (Анна Петрова, первый свободный слот `intro-call`)
независимо от тела запроса. Экран подтверждения показывает то, что вернул
сервер, поэтому на моке имя и время не совпадут с введёнными. Это отмечается
в `frontend/README.md`, чтобы не выглядело ошибкой.

## Маршруты

| Путь | Страница | Состояние |
|---|---|---|
| `/booking` | `BookingIndexPage` | Выбор типа встречи |
| `/booking/:eventTypeId` | `BookingPage` | Полный поток записи |

Неизвестный `eventTypeId` даёт 404 от API и страницу «Тип встречи не найден»
со ссылкой на `/booking`.


Карточка типа встречи нужна и на главной, и на `/booking`, поэтому переезжает
из `features/home/EventTypes.tsx` в `shared/ui/EventTypeCard.tsx`; обе страницы
используют её.

## Слой API

**`apiPost<T>(path, body, init?)`** в `client.ts` — та же обёртка над `fetch`,
что и `apiGet`: базовый URL, разбор JSON, `ApiError` на не-2xx. Поле `errors`
из тела 422 попадает в `ApiError.fieldErrors`, механика для этого уже есть.

**`endpoints.ts`** — четыре функции, каждая принимает `AbortSignal`:

| Функция | Запрос |
|---|---|
| `fetchEventTypes(signal)` | `GET /event-types` |
| `fetchEventType(id, signal)` | `GET /event-types/{id}` + `Prefer: example={id}` |
| `fetchAvailability(id, signal)` | `GET /event-types/{id}/slots` + `Prefer: example={id}` |
| `createBooking(request, signal)` | `POST /bookings` |

Заголовок `Prefer` формируется здесь и только здесь — одно место, один
комментарий с объяснением.

**`useApiResource<T>(loader)`** — общий хук загрузки: `{ data, isLoading, error,
retry }`, запрос на монтировании, `AbortController` на размонтировании, сброс
состояния в `retry`. `useEventTypes` из предыдущей итерации переписывается на
него — три почти одинаковых хука копировать незачем.

**`useBookingData(eventTypeId)`** — `useApiResource` с загрузчиком из
`Promise.all([fetchEventType, fetchAvailability])`, возвращает
`{ eventType, availability }`. Один индикатор загрузки и один алерт ошибки
вместо двух.

## Экран записи

**Заголовок.** Название типа встречи, длительность («30 мин»), описание.

**Дни.** Слева список всех 14 дней окна: `Ср, 5 авг · 4 слота`. Дни без
свободных слотов неактивны и помечены «нет слотов». По умолчанию выбран первый
день со слотами; если свободных слотов нет во всём окне — текст «На ближайшие
две недели свободных слотов нет».

**Слоты.** Справа сетка слотов выбранного дня кнопками-пилюлями с временем
начала. Выбранный слот подсвечен.

**Форма.** Раскрывается под колонками после выбора слота. Строка «Вы выбрали:
ср, 5 августа, 11:00 – 11:30», поля «Имя», «Email», «Комментарий»
(необязательный), кнопка «Записаться» с состоянием загрузки. Правила по
контракту: имя обязательно и до 200 символов, email обязателен и проверяется
выражением `/^\S+@\S+\.\S+$/` (глубокую проверку оставляем серверу),
комментарий до 1000 символов.

**Подтверждение.** После 201 вместо всего потока — карточка: «Вы записаны»,
название типа встречи, дата и время из ответа, имя и email гостя, комментарий
если есть. Ссылки «Записаться ещё раз» на `/booking` и «На главную» на `/`.

**Время.** Показывается в часовом поясе браузера, под сеткой слотов — подпись
«Время указано в вашем часовом поясе (Europe/Minsk)» с зоной из
`Intl.DateTimeFormat().resolvedOptions().timeZone`. В `POST /bookings` уходит
исходная строка `startAt` из ответа API без пересборки.

## Форматирование дат

`shared/format/datetime.ts` — чистые функции на `Intl` с локалью `ru-RU`.
Каждая принимает необязательный параметр зоны, по умолчанию — локальная.

| Функция | Пример результата |
|---|---|
| `formatDayLabel('2026-08-05')` | `Ср, 5 авг` |
| `formatTime('2026-08-05T11:00:00Z')` | `11:00` |
| `formatTimeRange(startAt, endAt)` | `11:00 – 11:30` |
| `formatDateTimeLong(startAt)` | `среда, 5 августа 2026 г., 11:00` |
| `currentTimeZone()` | `Europe/Minsk` |

Тесты не должны зависеть от зоны машины, поэтому `vite.config.ts` выставляет
`process.env.TZ = 'UTC'` до запуска Vitest.

## Ошибки

| Ситуация | Поведение |
|---|---|
| 404 на тип события | Страница «Тип встречи не найден» со ссылкой на `/booking` |
| Сеть или 5xx при загрузке | Алерт «Не удалось загрузить…» с кнопкой «Повторить» |
| 409 `slot_already_booked` | Предупреждение «Это время уже заняли, выберите другое», слоты перезапрашиваются, выбранный слот сбрасывается |
| 422 `validation_failed` | `errors[].field` раскладываются под поля формы через `setFieldError`, общий `message` — в алерт над кнопкой |
| Прочие ошибки `POST` | Алерт над кнопкой с `message` из ответа |

Форма остаётся заполненной при любой ошибке отправки: повторять ввод гость не
должен.

## Что осознанно не делаем

- Отмену и перенос брони — в контракте нет соответствующих ручек.
- Ручной выбор часового пояса.
- Ссылку «добавить в календарь» (`.ics`).
- Автоматический повтор `POST /bookings` — только явное действие гостя.
- Кеширование ответов между страницами.
- Содержимое админки — отдельная итерация.
