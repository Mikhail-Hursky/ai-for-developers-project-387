# Ночной Lighthouse — дизайн

Дата: 2026-08-17

## Задача

Ночью прогонять Lighthouse CLI по опубликованному приложению, утром команда
читает разбор и решает, нужны ли правки. Решение записывается там же, где лежит
разбор, — в issue.

Разбор пишет Claude: голая таблица баллов не отвечает на вопрос «а что чинить»,
а именно этот ответ нужен утром. Правки по разбору делает уже существующий
`claude-implement.yml` — по команде человека, не автоматически.

## Решения

| Вопрос | Решение |
|---|---|
| Что мерим | Прод на Railway, адреса `/` и `/admin` |
| Когда | `cron: '0 23 * * *'` — 02:00 по Минску, плюс `workflow_dispatch` |
| Чем | `npx lighthouse@13.4.1`, 3 прогона на адрес, в отчёт идёт медианный |
| Файл | Новый `.github/workflows/lighthouse.yml` |
| Сводка | `.github/scripts/lighthouse-summary.mjs` → `lighthouse-report/summary.md` |
| Пороги | `.github/lighthouse-thresholds.json`, читают и скрипт, и агент |
| Вердикт | 🔴 ниже порога, 🟡 падение ≥5 баллов к прошлой ночи, 🟢 остальное |
| Куда пишет | Один долгоживущий issue с лейблом `lighthouse`, комментарий за ночь |
| Режим action'а | Agent mode: `prompt` без `track_progress` |
| Права | `contents: read`, `issues: write`, `id-token: write` |
| Красный job | Только техническая ошибка; красный вердикт — это цвет комментария |
| Артефакты | HTML и JSON отчётов, `retention-days: 30` |

Не делаем: аудит страницы брони; автоматические правки и PR по итогам прогона;
падение job'а из-за низких баллов; хранение истории метрик вне треда issue;
тестовую обвязку для скрипта сводки.

## Почему прод, а не сборка в раннере

Локальный `vite preview` в раннере дал бы более чистые цифры, но не увидел бы
ничего из того, что добавляет доставка: заголовки кэширования, сжатие, отдачу
статики из FastAPI, задержки платформы. Ночная проверка нужна именно про то,
что видит пользователь.

Плата за это — шум. Он гасится тремя мерами: три прогона с выбором медианного,
прогрев перед замером и правило 🟡 по дельте ≥5 баллов, а не по любому
изменению.

## Почему медиана, а не один прогон

Публичный раннер делит CPU с соседями, и одиночный замер производительности
гуляет в пределах ±10 баллов. При правиле «просадка ≥5 баллов» это означало бы
жёлтый вердикт через ночь на ровном месте.

Скрипт берёт три отчёта по странице, сортирует по баллу производительности и
берёт средний **целиком** — все категории и все метрики из одного файла. Если
собирать медиану по каждой метрике отдельно, в отчёте окажется комбинация,
которой не было ни в одном реальном прогоне.

## Workflow

```yaml
name: lighthouse

on:
  schedule:
    - cron: '0 23 * * *'
  workflow_dispatch:

concurrency:
  group: lighthouse
  cancel-in-progress: false

permissions:
  contents: read
  issues: write
  id-token: write

env:
  BASE_URL: https://ai-for-developers-project-387-production-12f5.up.railway.app

jobs:
  lighthouse:
    name: lighthouse
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: '24'
      - name: Прогреть приложение
        run: curl --fail --silent --show-error --retry 5 --retry-all-errors
             --retry-delay 10 --output /dev/null "$BASE_URL/"
      - name: Прогнать Lighthouse
        run: # цикл по страницам × 3 прогона, см. ниже
      - name: Собрать сводку
        run: node .github/scripts/lighthouse-summary.mjs
      - name: Показать сводку в прогоне
        if: always()
        run: cat lighthouse-report/summary.md >> "$GITHUB_STEP_SUMMARY"
      - uses: actions/upload-artifact@v7
        if: always()
        with:
          name: lighthouse-report
          path: lighthouse-report
          if-no-files-found: warn
          retention-days: 30
      - uses: anthropics/claude-code-action@v1
        with:
          claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
          prompt: |
            # см. раздел «Промпт»
          claude_args: >-
            --allowedTools "Read,Glob,Grep,Bash(gh issue:*),Bash(gh label:*)"
            --max-turns 25
```

Здесь снимок структуры: тело цикла разобрано в разделе «Прогон CLI», промпт — в
разделе «Промпт», подробные комментарии будут в самом файле воркфлоу.

Адрес задан один раз в `env`: при передеплое сервиса меняется одна строка.

Шаг с `$GITHUB_STEP_SUMMARY` проверяет наличие файла перед `cat`: когда падает
скрипт сводки, job уже красный, и второй красный шаг подряд только запутывает.

Шаг агента идёт последним и без `if: always()` — если аудит не состоялся,
комментировать нечего. Сводка и артефакты, наоборот, заливаются всегда: когда
падает агент, ночные цифры не должны пропасть вместе с ним.

## Прогон CLI

```bash
npx --yes lighthouse@13.4.1 "$BASE_URL$path" \
  --output=json --output=html \
  --output-path="lighthouse-report/$slug-$i" \
  --chrome-flags="--headless=new --no-sandbox" --quiet
```

Версия зафиксирована намеренно: `latest` однажды приедет с новым мажором и
другой методикой подсчёта, и вся история дельт в треде обесценится. Обновление
версии становится отдельным осознанным коммитом.

Chrome на `ubuntu-latest` предустановлен, ставить его не нужно; `--no-sandbox`
обязателен — под пользователем раннера песочница не поднимается.

При двух `--output` Lighthouse дописывает к пути `.report.json` и
`.report.html`, поэтому скрипт сводки ищет `lighthouse-report/<slug>-<i>.report.json`.

Форм-фактор не задаётся — остаётся стандартная мобильная эмуляция с
троттлингом. Она строже десктопной, а цифры всё равно сравниваются сами с
собой от ночи к ночи.

Страницы:

| Адрес | slug |
|---|---|
| `/` | `home` |
| `/admin` | `admin` |

Страница брони не гоняется: хранилище бэкенда живёт в памяти процесса, после
передеплоя типов встреч нет, и `/booking/<slug>` может просто не существовать.
Заводить тип встречи из ночного прогона — значит писать в прод-данные ради
метрики; такой размен не берём.

## Пороги

`.github/lighthouse-thresholds.json`:

```json
{
  "performance": 90,
  "accessibility": 95,
  "best-practices": 95,
  "seo": 90,
  "deltaDrop": 5
}
```

Оба правила вердикта лежат в одном файле: абсолютные пороги читает скрипт,
`deltaDrop` — агент. Поднять планку можно правкой одной строки, не читая ни
скрипт, ни промпт.

## Скрипт сводки

`.github/scripts/lighthouse-summary.mjs` — Node без зависимостей. Читает JSON из
`lighthouse-report/`, для каждой страницы выбирает медианный по производительности
прогон и пишет `lighthouse-report/summary.md`:

- дату в поясе `Europe/Minsk` — прогон стартует в 23:00 UTC, то есть уже в
  следующих сутках по местному времени, и заголовок должен совпадать с тем, что
  команда считает «этой ночью»;
- таблицу: страница × четыре категории, баллы 0–100;
- строку `LCP · TBT · CLS` по каждой странице;
- строку `verdict: red|green` — результат сверки с порогами;
- список категорий, ушедших ниже порога, с указанием порога.

Скрипт отдаёт агенту компактный markdown вместо шести JSON по несколько сотен
килобайт: так дешевле по токенам и надёжнее — агенту не нужно ориентироваться
в структуре отчёта Lighthouse.

Вердикт по абсолютным порогам считает скрипт, а не модель: одинаковые цифры
должны давать одинаковый цвет каждую ночь.

## Промпт

Агент работает в agent mode: `prompt` без `track_progress`. Ветка и служебный
комментарий здесь не нужны — нужен ровно один комментарий в issue.

Порядок:

1. прочитать `lighthouse-report/summary.md` и `.github/lighthouse-thresholds.json`;
2. найти открытый issue с лейблом `lighthouse`
   (`gh issue list --label lighthouse --state open --limit 1`). Нет лейбла —
   создать через `gh label create`; нет issue — создать «Lighthouse: ночные
   прогоны», в теле описать, что это, как читать вердикт и как заказать правки;
3. взять последний комментарий бота в issue как базу для дельты
   (`gh issue view <n> --comments`); комментариев нет — первая ночь, дельты нет;
4. посчитать вердикт: 🔴 из `verdict: red`, иначе 🟡 при падении любой категории
   на `deltaDrop` и больше, иначе 🟢;
5. дописать комментарий в формате ниже;
6. при 🟡 и 🔴 — найти в коде причину просадки, опираясь на проваленные аудиты
   Lighthouse, и предложить правки.

Явные запреты: не коммитить, не открывать PR, не править код, не закрывать и не
редактировать чужие комментарии. Инструменты в `--allowedTools` это уже
ограничивают, но запрет проговаривается — ночью проверять некому.

## Формат комментария

Формат фиксированный: его разбирает агент следующей ночью, чтобы посчитать
дельту.

```
## 🟡 ночь на 18 августа

| Страница | Perf | A11y | Best practices | SEO |
|----------|------|------|----------------|-----|
| /        | 96 (=)  | 100 (=) | 100 (=) | 100 (=) |
| /admin   | 91 (−6) | 100 (=) | 100 (=) | 91 (=)  |

LCP 2.4 s · TBT 310 ms · CLS 0.00 (медиана трёх прогонов)
```

Дальше — по вердикту:

- 🟢 — одна строка «правки не нужны». Разбор не пишется: тридцать одинаковых
  простыней в месяц сделают тред нечитаемым, и настоящая проблема потеряется
  среди них;
- 🟡 и 🔴 — раздел «Что просело»: метрика, конкретный аудит Lighthouse, файл в
  репозитории, где причина. Затем «Что предлагаю»: список правок с оценкой
  влияния. Последняя строка — «Решение за командой».

В конце всегда ссылка на прогон и на артефакт с HTML-отчётами: подробности
смотрят там.

## Как правки попадают в работу

Отдельного механизма не строим. Утром команда отвечает в том же треде:

```
@claude implement — сделай пункт 2
```

Это `issue_comment` от владельца репозитория, то есть штатный триггер
`claude-implement.yml`: он заведёт ветку, прогонит проверки и откроет PR со
строкой `Closes #<номер>`. Issue и есть задача, решение остаётся за человеком.
Команда написана в теле issue, чтобы утром её не вспоминать.

## Один issue вместо issue за ночь

Новый issue каждую ночь завалил бы трекер тридцатью записями в месяц, каждую
пришлось бы закрывать руками. Долгоживущий issue держит всю историю в одном
месте, а дельта достаётся бесплатно — база лежит в прошлом комментарии, отдельно
хранить её не нужно.

Плата — растущий тред. Её гасят формат (зелёная ночь занимает пять строк) и
вердикт в первой строке комментария: тред листается по цветам заголовков.

## Красный job и красный вердикт — разные вещи

Job падает, только когда прогон не состоялся: приложение не ответило на
прогрев, CLI упал, скрипт сводки не смог разобрать отчёты. Тогда комментария за
ночь нет, и молчание вместе с красным чеком в Actions читается однозначно.

Низкие баллы job не роняют. Иначе бейдж репозитория висел бы красным из-за 89
баллов производительности, и через неделю на него перестали бы смотреть.

## Проверка

Разовая, тестовой обвязки в `.github/` не заводим.

1. `actionlint .github/workflows/lighthouse.yml` — если линтер есть в системе;
   иначе синтаксис проверит GitHub на первом прогоне.
2. Скрипт сводки локально: сохранить реальные JSON в `lighthouse-report/`,
   прогнать `node .github/scripts/lighthouse-summary.mjs`, сверить таблицу,
   медиану и вердикт глазами.
3. Первый `workflow_dispatch`: в артефактах шесть JSON и шесть HTML, в job
   summary — таблица, в трекере появился issue с лейблом `lighthouse` и первым
   комментарием без дельты.
4. Второй `workflow_dispatch`: в issue второй комментарий, в нём проставлены
   дельты, при зелёном вердикте — без разбора.
5. Красный путь: временно поднять порог в `.github/lighthouse-thresholds.json`
   заведомо выше текущих баллов, прогнать, убедиться, что пришёл разбор с
   файлами репозитория, вернуть порог.
6. Связка с утром: `@claude implement` в треде поднимает `claude-implement`,
   а `lighthouse` при этом не запускается.

## Известные ограничения

- **Шум раннера.** Медиана трёх прогонов сокращает разброс, но не убирает;
  редкие ложные 🟡 по производительности возможны.
- **Cron неточен.** GitHub запускает расписание с задержкой до получаса в часы
  пик и отключает `schedule` после 60 дней без активности в репозитории.
- **Пустое хранилище прода.** После передеплоя главная показывает пустой список
  типов встреч, DOM меньше реального — баллы главной оптимистичнее.
- **Страница брони не покрыта**, а это самая тяжёлая часть интерфейса.
- **Тред растёт.** Раз в несколько месяцев issue стоит закрывать руками;
  следующей ночью агент заведёт новый.
- **Токены тратятся каждую ночь**, включая зелёные.
- **Регресс привязан ко времени, а не к коммиту.** Отчёт говорит, что стало
  хуже, но не показывает, какой деплой это сделал.
