# Фронтенд: страница админки — дизайн

Дата: 2026-08-04

## Задача

Реализовать два сценария владельца календаря на `/admin`:

- создание типа события — владелец задаёт `id`, название, описание
  и длительность в минутах;
- просмотр предстоящих встреч — единый список броней всех типов событий.

Заглушка «Скоро» заменяется рабочей страницей. Бэкенд по-прежнему не пишем:
работаем против Prism-мока из `spec/` (см. [дизайн мока](2026-08-02-prism-mock-design.md),
[дизайн главной](2026-08-02-frontend-home-design.md) и
[дизайн страницы записи](2026-08-02-booking-page-design.md)).

Обе ручки уже описаны контрактом и отдаются моком:
`POST /admin/event-types` и `GET /admin/bookings/upcoming`.

## Решения

| Вопрос | Решение |
|---|---|
| Структура страницы | `Tabs`: «Предстоящие встречи» (по умолчанию) и «Типы встреч» |
| Состояние вкладки | Query-параметр `?tab=`, читается через `useSearchParams` |
| Вкладка типов | Список существующих типов + кнопка «Создать тип», форма в `Modal` |
| Список встреч | Карточки с группировкой по календарному дню |
| Группировка по дням | Местный часовой пояс браузера, ключ дня через `Intl` |
| Форма | `@mantine/form`, валидация повторяет ограничения контракта |
| Уведомление об успехе | `Alert` над списком; `@mantine/notifications` не подключаем |
| Совместимость с моком | Созданный тип дописывается в список локально, как его вернул сервер |

Не делаем: редактирование и удаление типов событий, фильтры и пагинацию
списка встреч, авторизацию. Контракт таких ручек не описывает, требование
их не содержит.

## Ограничения мока

Два ограничения Prism касаются создания типа события.

**Состояние не хранится.** Тип, созданный через `POST /admin/event-types`,
не появится в ответе `GET /event-types`. Чтобы владелец видел результат своего
действия, вкладка «Типы встреч» держит локальный список созданных типов и
склеивает его с ответом ручки, отсеивая дубликаты по `id` (на реальном бэкенде
дубликатов не будет — там тип вернётся из ручки).

**Ответ фиксирован.** Как и `POST /bookings`, ручка всегда возвращает одну и ту
же фикстуру — `strategy-session` «Стратегическая сессия», 90 минут — независимо
от тела запроса. Список и алерт показывают то, что вернул сервер, поэтому на
моке созданный тип не совпадёт с введённым. Отрисовывать введённые значения
вместо ответа мы не будем: с настоящим бэкендом это скрыло бы расхождения.
Отсюда же следует, что повторное создание на моке даёт в списке один и тот же
`strategy-session` — дедупликация по `id` это гасит.

Оба ограничения документируются комментарием в коде и разделом «Особенности
работы с моком» в `frontend/README.md`, чтобы не выглядели ошибкой.

## Маршруты

| Путь | Страница | Состояние |
|---|---|---|
| `/admin` | `AdminPage` | Вкладка «Предстоящие встречи» |
| `/admin?tab=event-types` | `AdminPage` | Вкладка «Типы встреч» |

Неизвестное значение `tab` трактуется как значение по умолчанию.
Новых маршрутов в `App.tsx` не появляется.

## Структура

```
frontend/src/
  pages/

  features/admin/

  shared/api/

    useUpcomingBookings.ts        хук поверх useApiResource
```

`AdminPage` не содержит запросов: за данные отвечают компоненты вкладок.

## Слой API

`CreateEventTypeRequest` повторяет поля `EventType` — по контракту это
`...EventType`, все четыре поля задаёт владелец.

```ts
export function fetchUpcomingBookings(signal: AbortSignal): Promise<Booking[]>;
export function createEventType(
  request: CreateEventTypeRequest,
  signal?: AbortSignal,
): Promise<EventType>;
```

Заголовок `Prefer` этим ручкам не нужен: примеров, выбираемых по идентификатору,
у них нет.

`useUpcomingBookings()` — по образцу `useEventTypes`: `useCallback` вокруг
загрузчика и `useApiResource` сверху. Отмена запроса и `retry` достаются даром.

## Вкладка «Предстоящие встречи»

Четыре состояния по устоявшемуся в проекте паттерну:

1. загрузка — `Skeleton`;
2. ошибка — `Alert` с кнопкой «Повторить» (`retry` из `useApiResource`);
3. пусто — «Предстоящих встреч пока нет»;
4. данные — список карточек.

Ручка отдаёт брони уже отсортированными по возрастанию `startAt`, поэтому
клиент не сортирует, а только режет список на группы по дням, сохраняя
порядок. День считается в местном поясе браузера: гость и владелец видят
одинаковое локальное время.

В `shared/format/datetime.ts` добавляются две функции:

- `localDateKey(isoDateTime)` → `2026-08-05` — ключ группировки; берётся
  из `Intl.DateTimeFormat('en-CA', { timeZone })`, который даёт готовый
  `YYYY-MM-DD` без ручной арифметики со смещениями;
- `formatDateLong(isoDateTime)` → `среда, 5 августа` — заголовок группы.

Существующий `formatDayLabel` для этого не годится: он форматирует
календарную дату окна записи в UTC, а здесь нужен день момента времени
в местном поясе.

Карточка встречи показывает: время (`formatTimeRange`), `Badge` с названием
типа события, длительность в минутах, имя гостя, email ссылкой `mailto:`
и комментарий, если он есть. Под списком — подпись о часовом поясе
(`currentTimeZone()`), как в потоке записи.

## Вкладка «Типы встреч»

Список существующих типов приходит из `useEventTypes` — того же хука,
что использует главная. Витринный `EventTypeCard` не переиспользуется:
он ведёт ссылкой на бронирование и не показывает `id`, а владельцу `id`
важен — он его задаёт сам и по нему получает 409. Вместо карточки —
компактная строка: название, `Badge` с `id`, длительность, описание.

Состояния списка те же четыре, что и у встреч; пустое — «Типы встреч пока
не созданы».

Кнопка «Создать тип» открывает `Modal` с формой. После успешного создания
модалка закрывается, тип добавляется в локальный список, над списком
появляется зелёный `Alert` «Тип встречи "…" создан». Алерт скрывается при
следующем открытии модалки.

## Форма создания типа события

`@mantine/form`, валидация повторяет ограничения контракта:

| Поле | Контроль | Правило |
|---|---|---|
| `id` | `TextInput` | Обязательное, `^[a-z0-9]+(-[a-z0-9]+)*$`, ≤ 100 символов |
| `name` | `TextInput` | Обязательное, ≤ 150 символов |
| `description` | `Textarea` | ≤ 2000 символов, пустое допустимо |
| `durationMinutes` | `NumberInput` | Целое от 1 до 1440 |

Сообщение об ошибке `id` объясняет формат: «Латиница в нижнем регистре,
цифры и дефисы, например intro-call».

Ошибки сервера обрабатываются как в `GuestForm`: ошибка поля берётся из
`form.errors.<field> ?? fieldErrors.<field>`.

| Ответ | Поведение |
|---|---|
| `409 event_type_already_exists` | Ошибка на поле `id`: «Тип события с таким id уже существует» |
| `422 validation_failed` | `errors` раскладываются по полям, `message` — в общий `Alert` |
| Прочее (в том числе `network_error`) | Общий `Alert` в модалке |

При любой ошибке модалка остаётся открытой, введённые значения сохраняются.
Кнопка отправки — в состоянии `loading` на время запроса.

## Тесты

`src/test/stubFetch.ts` расширяется: сейчас `url.endsWith('/event-types')`
перехватил бы и `POST /admin/event-types`, а `/bookings` — и
`GET /admin/bookings/upcoming`. Ветки админских путей проверяются
**до** гостевых.

В `src/test/fixtures.ts` добавляются фикстуры предстоящих встреч (минимум
две брони разных типов в разные дни — чтобы проверить группировку) и
созданного типа события.

Покрытие:

| Файл | Проверяем |
|---|---|
| `AdminPage.test.tsx` | Вкладка по умолчанию, переключение вкладок |

| `EventTypesAdmin.test.tsx` | Успешное создание: тип в списке и алерт; 409 → ошибка на поле `id` |
| `EventTypeForm.test.tsx` | Клиентская валидация `id`, `name`, `durationMinutes` |
